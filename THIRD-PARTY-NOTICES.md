# Third-party notices

Bleephub vendors and redistributes the following third-party material. Anything
that ships inside a published container image is marked as such, because that is
where redistribution obligations attach.

Bleephub itself is AGPL-3.0-or-later ([LICENSE](LICENSE)). Every entry below is
one-way compatible with that, and inbound dependencies have to stay that way.

Every artifact a build downloads is pinned to an immutable version or commit and
verified against a SHA-256 recorded here before it is used. Where something
genuinely cannot be pinned — a floating apt repository — the entry says so and
states what is pinned instead.

## dqlite — LGPL-3.0 with a linking exception — **redistributed in the server image**

`libdqlite0` links into `bleephub-dqlite-node`; its headers build that binary.
Both come from Canonical's dqlite PPA.

| | |
|---|---|
| Upstream | https://github.com/canonical/dqlite |
| Repository | `https://ppa.launchpadcontent.net/dqlite/dev/ubuntu noble main` |
| Signing key | vendored at `docker/dqlite-ppa.asc`, fingerprint `392A47B5A84EACA9B2C43CDA06CD096F50FB3D04` ("Launchpad PPA for dqlite"), SHA-256 `6204653dd8f82bb35615f572ccc795cf2d4f5b388b76a8d940e9e01a764e9cc5` |
| Enforced by | `signed-by=` in the sources entry: apt accepts the repository only if it is signed by that key. `add-apt-repository` used to fetch the key from Launchpad at build time and trust whatever came back |
| Licence | LGPL-3.0 with a special exception for statically or dynamically linked combined works (https://github.com/canonical/dqlite/blob/master/LICENSE) |

**Residual risk:** the PPA publishes exactly one version of each package and
drops the previous one — on 2026-07-27 it offered `libdqlite0` and
`libdqlite-dev` at `1.18.3~noble1` and nothing older — so an `apt-get install
libdqlite0=<version>` pin would break the build the day upstream rebuilds. The
package versions therefore float; what is pinned is the key that has to have
signed them. Tracked as `CI-028`.
